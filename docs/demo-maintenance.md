# Maintaining the demo and documentation media

The hosted demo is built from the same frontend source as the Go application.
It is not a separately maintained copy of the UI.

## Outputs and publication

| Output | Command (from web/) | Destination | Tracked? |
| --- | --- | --- | --- |
| Frontend embedded in the Go binary | `npm run build` | `internal/webassets/dist/` | Yes; include regenerated output with frontend changes |
| Standalone browser demo | `npm run build:demo` | `site/` | No; generated by Pages CI |

The demo build enables synthetic data at compile time and sets the asset base to
`/kubeaquarium/`. It needs no backend or Kubernetes connection, even without `?demo`.
Validate the built output under that base path, not only the Vite development server.

After building, start the preview from `web/`:

```sh
npm run preview -- --host 127.0.0.1 --port 7782 --outDir ../site --base /kubeaquarium/
```

From the repository root, run `node video/scripts/check-static-demo.mjs`. It checks
loading without a demo query flag, all vessel selections and persistence, and zero
API requests, WebSockets, or browser errors.

`.github/workflows/pages.yml` rebuilds and publishes `site/` on pushes to `main`,
and also supports manual dispatch. Opening a PR does not publish its demo. After
an authorized merge, check the Pages workflow and the hosted demo.

`.github/workflows/ci.yml` runs on PRs. It type-checks and builds the frontend and
static demo, runs Go tests and vet, builds
the binary, and smoke-tests its version command. Browser interaction and media
review must also run locally; a green build alone does not validate those.

## Media freshness

Apply [review-demo-media](../skills/review-demo-media/SKILL.md) before delivery.
Screenshots referenced by the README live in `docs/screenshots/visual-feedback/`.
The README GIF, MP4, and poster live in `docs/video/`; their capture and render
pipeline is documented in [video/README.md](../video/README.md).

For visual or workflow changes:

1. Test the affected behavior against the local simulated demo. For fleet and
   navigation changes, `video/scripts/check-playthrough.mjs` records actual
   keyboard movement and steering for all three vessels and checks persistence.
2. Run `video/scripts/capture-visual.mjs` from the repository root with `DEMO_URL`
   set to the local demo. Inspect desktop and narrow captures.
3. Follow the video capture/render steps, inspect the rendered frames and
   recording, and regenerate the poster and GIF with the MP4.
4. Rebuild both frontend outputs, verify README media links, and record the
   validation result. Preserve historical benchmark evidence instead of
   overwriting it with results from a newer implementation.

All automated destructive interactions use synthetic local data and the existing
network guards. Media refresh does not require access to a real cluster.

## Social link previews

Open Graph and large-image Twitter card tags are present in `web/index.html`, so
preview crawlers can read them without running JavaScript. Absolute metadata URLs
point to the public GitHub Pages demo. The 1200×630 image is
`web/public/social/kubeaquarium.png`, copied into both build outputs.

Regenerate it with `node video/scripts/make-social-preview.mjs` from the repository
root. This reuses the launch artwork and bundled font. Review the image, rebuild
both outputs, and check the deployed HTML and image URL after Pages completes.
Include this card in media-freshness reviews when branding or share copy changes.
